## 2. NetSurf buildsystem — `git://` only ⚠️

MacSurf does **not** vendor the buildsystem; its lib Makefiles expect it at
`$(PREFIX)/share/netsurf-buildsystem`.

- `https://github.com/netsurf-browser/netsurf-buildsystem.git` → **404**
- `https://git.netsurf-browser.org/buildsystem.git` → **404**
- **`git://git.netsurf-browser.org/buildsystem.git` → works**

The unencrypted `git://` protocol is the only route found. Many networks and CI
providers block it. **Mirror this repo ourselves before depending on it** —
it is a single point of failure for the whole build.

### 3.1 `-Werror` must be dropped

NetSurf's buildsystem compiles with `-Werror` and a strict warning set
(`-Wnested-externs`, `-Wunused-variable`, …). **MacSurf's own debug
instrumentation violates it**:

```
src/libwapcaplet.c:212: error: nested extern declaration of
    'macsurf_debug_log_writef' [-Werror=nested-externs]
src/libwapcaplet.c:308: error: unused variable 'sa_' [-Werror=unused-variable]
```

Instrumentation inside the five nominally-portable libraries:

| Library | `macsurf_debug_log_writef` call sites | Files |
|---|---:|---:|
| libcss | 12 | 3 |
| libdom | 10 | 1 |
| libwapcaplet | 6 | 1 |
| libhubbub / libparserutils | 0 | 0 |

**28 call sites across 5 files.** Small and tractable — provide the symbol (or
a no-op macro) rather than stripping it; it is useful logging. `WARNFLAGS="-Wall"`
unblocks the build meanwhile.

### 3.3 Generated sources are vendored — gperf not actually required

MacSurf builds with CodeWarrior on Mac OS 9, which has no gperf or perl, so the
generated files are **committed**:

- `libparserutils/src/charset/aliases.inc` (52,752 bytes)
- `libhubbub/src/treebuilder/autogenerated-element-type.c` (27,724 bytes)

`make` only tries to regenerate them when their mtimes look stale — which a
`cp -r` causes. `touch` the generated files after copying and generation is
skipped entirely.

One real gotcha: `aliases.c` does `#include <aliases.inc>` with **angle
brackets**, so `-Isrc/charset` must be on the include path. Upstream this works
because the generated file lands in the build directory.

## 4. MacSurf's NetSurf Makefiles are stale — important

Two independent pieces of evidence:

1. `src/charset/encodings/Makefile` builds `utf8.c`; the file in the tree is
   **`pu_utf8.c`** (renamed, presumably for a CodeWarrior symbol collision).
   The Makefile was never updated.
2. `libcss/include/libcss/functypes.h` includes `macsurf_alloc_override.h`,
   which lives in `frontends/macos9/` — not on any include path the lib
   Makefile sets.

**MacSurf does not build via these Makefiles.** It builds from `MacSurf.mcp`,
a CodeWarrior project. The NetSurf Makefiles in the tree are inherited and
unmaintained.

**Consequence:** restoring a working Makefile build is *our* work, not
something we inherit. This is another argument for brief §14.4's patch stack —
vendor **upstream NetSurf** (whose Makefiles do work) and apply MacSurf's
changes as patches, rather than adopting a tree whose build system has rotted.

## 5. ⭐ `harness/` — MacSurf's own Linux port roadmap

`harness/BUILD-NOTES.md` (45 lines) documents MacSurf's effort to build the
engine **and** the QuickJS bridge on Linux under AddressSanitizer, to debug a
use-after-free off-hardware. It is effectively a porting guide written by
someone who already knows where the bodies are.

### 5.1 It independently confirms brief §14.2

On building NetSurf core on Linux, their Layer 3 option (B):

> *"reuse `browser/netsurf/frontends/monkey` — it already builds headless
> NetSurf core on Linux via the NetSurf Makefile; swap/add our QuickJS binding.
> The core-on-Linux 90% is done for us; delta is the JS binding."*

That is brief §14.2/§14.3 reached independently. **Adopt it.**

### 5.2 The Mac OS 9 decoupling surface is small

Layer 4 states the bridge needs only:

- **12 `#ifdef __MACOS9__` blocks** compiled out (do *not* define `__MACOS9__`)
- **3 stub headers**: `macos9.h` (type + extern decls, **no Carbon**),
  `macsurf_debug.h` (→ printf/no-op), `macsurf_timebase.h` (→ `clock_gettime`)

This materially shrinks the §13.2 seam risk: the bridge's Mac coupling is 12
conditional blocks and 3 headers, not a pervasive entanglement. The *networking*
re-host (`macos9_js_fetch.c`) remains the real work.

### 5.3 Use `quickjs-macos9/`, not `browser/libquickjs/`

> *"Use the COMPLETE `quickjs-macos9/` tree (not `browser/libquickjs/`, which is
> missing the generated headers `quickjs-c-atomics.h` /
> `builtin-array-fromasync.h`)."*

Working Linux compile line they give (per file: quickjs, libregexp, libunicode,
dtoa):

```sh
gcc -c -O1 -g -fsanitize=address -pthread -D_GNU_SOURCE -include pthread.h \
    -DCONFIG_VERSION='"harness"' -I. <file>.c -o <file>.o
```

Gotchas they already paid for:
- **Never define `MAC_OS_9` on Linux** — pulls in Toolbox types (`UnsignedWide`).
- `cutils.h` uses `PTHREAD_CREATE_DETACHED` without including `<pthread.h>` →
  `-include pthread.h`.
- QuickJS-ng needs generated headers, present only in `quickjs-macos9/`.

### 5.4 Ready-made probe corpora

`harness/` ships real production bundles: `fbcdn.net-css-v5.css`,
`fbcdn.net-loader-b25.js`, `hackaday-bundle.js`, `core-compiled.js`, a webp
corpus and woff2 fonts. These are exactly the "probe cards" brief §8 and §14.3
call for, already collected — **and they are heavy-SPA assets**, directly
relevant to the north star.

### 5.5 Their status

Layer 1 (QuickJS under ASan) ✅ done. **Layers 2–5 not done.** So the Linux
harness is a validated plan with one layer complete, not a finished tool. We
would be continuing it, not inheriting it.
