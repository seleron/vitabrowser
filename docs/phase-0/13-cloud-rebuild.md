# 13 — Rebuilding from the repo alone (cloud session, 2026-09-27)

The build loop paused on 2026-09-27 ~12:57 with Patch 131 (B1 streaming)
mid-flight: its C/JS edits existed only in the desktop's applied tree
(`<WORK>/vitabrowser-work/applytest/upstream/netsurf`), which is uncommitted by
design. The desktop was offline, so this session rebuilt everything from
the repository and GitHub, then re-did Patch 131 from scratch. This
document records what that took, because a from-scratch rebuild had never
been done before and it found four problems (a fifth, an upstream libcss
bug, turned up once the monkey tests ran again: section 4).

## 1. Reproducing the work tree: `tools/bootstrap-work.sh`

The original trees came from `git://git.netsurf-browser.org` and their
revisions were never recorded (docs 01, 02). The cloud runner cannot reach
netsurf-browser.org, savannah.gnu.org, curl.se or web.archive.org
(egress policy), so the script uses GitHub only:

| MacSurf `browser/` | `mplsllc/macsurf` | `55e64fa` (unchanged) |

With these pins the committed stack applies **215/215** and
`nsvita-sim` builds.

### Finding 1: the MacSurf patches assume BUILT upstream trees

On freshly cloned trees `libcss/08-parse-properties.patch` and
`libhubbub/04-treebuilder.patch` fail with "can't find file to patch".
They patch files the build generates (libcss's `autogenerated_*.c` from
`properties.gen`, libhubbub's `autogenerated-element-type.c` via gperf).
Those files are gitignored, so the desktop's "pristine" trees (built in
place during Phase 0) passed `build-patched.sh`'s `git status` check while
still carrying them, and `split-patches.py` diffed against them.

Fix: `bootstrap-work.sh` builds the five core libraries in place once
(needs `gperf`), which recreates the files; the trees stay git-clean.

### Finding 2: patch 46 was corrupt, masked by the in-place workflow

`a45dc70` (Patch 130) hand-edited `46-netsurf-vita-quickjs-bridge.patch`
to add the "re-read `vita_window_current()` after `vita_schedule_run()`"
fix. It added 6 lines but changed the hunk header from `+834,10` to
`+834,12` (should have been `+834,16`), so `git apply` reported "corrupt
patch at line 334" and GNU `patch` rejected it. The desktop never noticed
because its applied tree is edited in place and not re-applied from the
repo. The broken patch also cascaded: 47, 48, 49, 50 and 54 failed after it.

The fix also belonged to Patch 130, not 46: `vita_window_current()` only
exists after the popup patches (126/127). So patch 46 is restored to its
pre-`a45dc70` text, and the fix moves to the end of patch 130. It now
re-reads `bw` as well as `gw`, since a closed popup frees its
browser_window too and `bw` was derived from the freed `gw`.

**Lesson (hard rule proposal):** never hand-edit an old patch file. Put
late fixes in the newest patch, and after any patch commit run
`tools/apply-patches.sh` on a fresh stage (`tools/build-patched.sh` does
this).

### Finding 3: `nsmonkey` no longer links

`build-patched.sh`'s final `nsmonkey` link fails on symbols only the Vita
frontend provides (`js_fire_window_load`, `js_link_frame_heaps`,
`svgtiny_*`). The simulator (`run-vita-sim.sh`) doesn't need the monkey
binary (it needs the prefix and the patched tree), so this is cosmetic. It
does mean the golden-plotstream checks (doc 03) have not run since the
QuickJS bridge landed.

### Finding 4: the simulator linked the wrong libparserutils, so every page was blank

The first full suite run here (exit 1) failed only at
`21-NET-https-rogue: LOADED OR MISSING`. The real failure was much bigger:
**every** page, `file:` ones included, failed in `html_create` with
`DOM_HUBBUB_HUBBUB_ERR_BADENCODING` (215 "content create FAILED" in
netsurf.log). `run-vita-sim.sh` builds a `WITHOUT_ICONV_FILTER`
libparserutils overlay because the stand-in libc's `iconv_open` always
fails, as newlib's does on the Vita. It relied on `PKG_CONFIG_PATH` order to
link that overlay, but pkgconf 1.8 (Ubuntu 24.04) prints the engine
prefix's `-L` first, so the iconv libparserutils was linked instead. The
network checks compare NET pages with L1, and two blank pages compare
equal, so they passed. Only the rogue-certificate check, which looks for
a page title, noticed.

Fix: the overlay leads `LDFLAGS` (which the frontend Makefile appends to),
and the suite now fails if the first page run has any failed content
creation. An `nm` check for glibc `iconv` was tried first and dropped: it
cannot tell the two libraries apart, because NetSurf's `utils/utf8.c`
references iconv itself.

It is unknown whether the desktop's pkg-config ordered these the other way,
or whether its runs had the same blind spot. Its reported JS and
interaction passes suggest pages did render there.

### Script changes for sandboxed machines

- `build-patched.sh`: `SKIP_REGEN=1` builds the committed stack as-is
  instead of regenerating the MacSurf patches first.
- `build-host-freetype.sh`: falls back to SourceForge for the same
  tarball (the SHA256 pin is the check).
- `fetch-certs.sh`: `CA_BUNDLE_LOCAL=<file>` stands in for the pinned
  Mozilla bundle, with a loud warning. Simulator only: never package a VPK
  built this way.

Full recipe on a new machine:

    apt-get install gperf flex bison      # plus the usual build tools
    tools/bootstrap-work.sh
    SKIP_REGEN=1 tools/build-patched.sh   # nsmonkey link failure is expected
    CA_BUNDLE_LOCAL=/etc/ssl/certs/ca-certificates.crt tools/run-vita-sim.sh

## 2. Patch 131: streaming transport (B1 / S5)

Rewritten from scratch; the design is in the patch header
(`patches/vitabrowser/131-netsurf-streaming-xhr-eventsource.patch`). In
short: FETCH_DATA schedules one de-duplicated progress tick per scheduler
pass, JS pulls new bytes with `__xhrNativeTake(id, discard)` (cut at a
UTF-8 boundary), XHR walks OPENED→HEADERS_RECEIVED→LOADING→DONE with
`progress` events, and `EventSource` is a spec parser with reconnect and
`Last-Event-ID`.

Two bugs in the committed test setup meant the gate could never have
passed:

- `JS-streaming.html` compared `readyState`, a number, with the strings
  `'1'`/`'2'`/`'3'`, so rows 1 and 3 could never pass.
- `httpd.py` sent `Transfer-Encoding: chunked` on Python's default HTTP/1.0
  status line. curl de-chunks only HTTP/1.1, so the chunk framing would have
  reached the page as body.

A third was timing: the autotest dumps a page after 0.7 s without a
repaint (`VITA_SETTLE_MS`), and the page only repainted when a row changed.
Run 5 therefore dumped it before `close()` at 5 s over http (6/7), and
before any result over https (no summary line). The page now closes the
source as soon as rows 4–6 pass and ticks a line until every row has
resolved. The engine was deliberately not changed here: an open
EventSource must not stop a real page from ever counting as settled.

Unit checks outside the simulator: the EventSource parser against mocked
natives in Node (13/13: CRLF/CR/LF splits across chunks, BOM, comments,
multi-line data, `id` reset, `retry`, reconnect with Last-Event-ID, 500 and
wrong Content-Type fail for good, `close()` inside a handler stops
dispatch); the UTF-8 cut on 1–4-byte sequences.

## 3. Patch 132: streaming `fetch()` bodies (B1, part 2)

claude.ai, like the Anthropic SDK, reads its event stream with
`fetch(url).then(r => r.body.getReader())`. Before this patch the engine had
no `ReadableStream`, and `fetch()` resolved only at DONE with a text-only
`Response`. The design is in the patch header
(`patches/vitabrowser/132-netsurf-streaming-fetch-bodies.patch`):

- a native `__xhrNativeTakeBytes`, returning exact bytes;
- streams in the polyfill;
- a `Response` whose body is a stream of `Uint8Array`;
- a `fetch()` that starts the request at call time, resolves at the first
  body bytes and feeds the body from the Patch 131 progress ticks. Cancel
  and abort stop the native fetch.

The Node harness caught one real issue before the simulator ran: the
request started a microtask late for every body. It now starts
synchronously unless the body has to be read first (a Blob or a stream).

## 4. Patches 133 + 134: nsmonkey back, and an upstream libcss clip bug

**Patch 133, nsmonkey links again.** Finding 3 is fixed. Monkey builds
NetSurf's default Duktape backend, while `html.c` and `desktop/frames.c`
called two QuickJS-only hooks (`js_fire_window_load`,
`js_link_frame_heaps`), and patch 121's inline SVG needs libsvgtiny,
which monkey's defaults left out. The two calls are now under
`WITH_QUICKJS`, and monkey builds with `NETSURF_USE_NSSVG`. The Vita and
simulator builds are unchanged: they define `WITH_QUICKJS`.

With monkey back, the checks it feeds turned out to have drifted since
patch 32, when they last ran:

- `testpages/patched-streams/` was refreshed. The differences are the
  intended later paint work: patch 97 paints an outer shadow as the strips
  outside its box (the spec's clipping), not one rect under it.
- `tools/test-vita-renderer.sh` did not compile: `plot.c` has needed
  `pathfill.c` since patch 124. The ink-clip checks in `test_vita_plotter.c`
  looked for the one-rect shadow; they now check each strip against the
  clip in force.

**Patch 134, clip rect units (upstream libcss bug).** Rewriting those
checks showed PM-shadow-clip's negative control clipping at the viewport
(x 951), not at its `clip: rect(0, 200px, 60px, 0)` edge (x 500). libcss's
`get_clip()` unpacked the top and right units as
`bits & 0x3e00000 >> 21` / `bits & 0x1f0000 >> 16`, which C parses as
`bits & 0x1f`: the clip type and auto flags, 2 (`em`) for a plain rect.
The right edge was therefore 200em. The bug is present in pristine
upstream libcss (`499f1c4`) and is worth sending upstream. It is fixed in
the generator input (`overrides.py`) and in the committed
`autogenerated_propget.h`. The renderer test now also checks the right
edge.
